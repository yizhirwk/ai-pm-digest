## PM Concept of the Day: Cutover Strategy (Big Bang vs. Phased vs. Parallel Run)

When a project replaces a critical system — like Deutsche Bank retiring 15 legacy core banking platforms for two Vault Core instances — the PM has to choose a **cutover strategy** for how the transition from old to new actually happens. A **big bang** cutover switches everyone to the new system at once (fast, but high-risk if something breaks); a **phased cutover** migrates users, products, or regions in stages (lower risk per stage, but longer overall exposure to running two systems); and a **parallel run** keeps both old and new systems live and processing the same transactions side by side for a period, comparing outputs before fully decommissioning the old one. Deutsche Bank is explicitly using this last approach — running old and new systems in parallel through testing before staged product migration starts in 2027 — because for a bank, an undetected discrepancy in account balances or lending calculations is far costlier than the extra time and infrastructure cost of running two systems at once. Choosing the wrong cutover strategy for the risk profile (e.g., big-banging a payments core instead of running it in parallel first) is a classic PMP-style scenario question, since it tests whether a candidate weighs risk tolerance and reversibility, not just speed.

## One Thing to Try Today

Spend 10-15 minutes sketching a one-page cutover plan for a hypothetical system replacement in your own work (or Deutsche Bank's Vault Core migration as a stand-in): pick one of the three strategies above, then write three concrete rollback triggers — specific conditions that would tell you to pause the migration and fall back to the old system. Practicing rollback-trigger thinking now builds the instinct examiners and real stakeholders both expect before you're the one signing off on a live cutover.
