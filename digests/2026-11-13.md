## PM Concept of the Day: Non-Functional Requirements (NFRs)

Non-functional requirements describe *how well* a system must work rather than *what* it does. Examples are availability, latency, throughput, security, recoverability, auditability and scalability. In PMI terms they belong in the requirements documentation and the Requirements Traceability Matrix just like features do. In Agile they usually appear as constraints on the backlog or as part of the Definition of Done, not as standalone stories. They are a common source of late surprises because nobody "demos" an NFR. A payment API that works perfectly in sprint review can still fail go-live if no one specified "p99 authorization latency under 300 ms at 2,000 TPS" or "RPO of zero, RTO of 15 minutes."

The UK manifesto's push to treat payments as critical national infrastructure is essentially a call for stricter NFRs on resilience and recovery. A fintech PM should capture NFRs early, make each one measurable, assign an owner, and plan the performance, failover and security testing that proves them.

## One Thing to Try Today (10 minutes)

Pick a payments feature you know, such as "send money to a contact" in a banking app. Write five non-functional requirements for it, one each for:

1. Availability
2. Latency
3. Security
4. Audit logging
5. Disaster recovery

Make each one testable, with a number and a condition. For example: "99.95% monthly availability, excluding scheduled maintenance announced 72h ahead." Then, next to each NFR, note *how* you would verify it before launch, such as a load test, failover drill or pen test. That turns a wish list into a test plan.
